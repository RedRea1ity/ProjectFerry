# 摆渡计划 · 「拖入任意游戏自动汉化」评估

> 状态：**只有方案，没有一行代码**。2026-11-04 起草，给牢红「想想」用。
> 凡未验证的都写明「未验证」，不把设想说成能力。

---

## 0. 一句话结论

这个愿望不是一个功能，是 **七个不同的工程** 加 **两条互斥的产品路线**。
摆渡现有代码能复用的比你预期的少，但**方法论能复用的比你预期的多**。

---

## 1. 先把愿望拆成六步

「自动汉化」实际上永远是这六步。摆渡在 MC 上做掉了其中四步，但每步的含金量差很远：

| 步骤 | MC 里怎么做的 | 换个游戏还成立吗 |
|---|---|---|
| ① 找到文本 | 扒 jar 的 class 常量池 + lang 文件 | ❌ 每个引擎完全重写 |
| ② 判断该不该翻 | 英文关键词过滤 + sink 分析 | ⚠ 方法论通用，规则要重写 |
| ③ 翻译 | LLM + 术语表 + 社区语料 | ✅ **完全通用** |
| ④ 回写 | 生成资源包 lang 覆盖层 | ⚠ 「不碰原文件、旁挂覆盖」的思路通用，格式重写 |
| ⑤ 生效 | 资源包加载 / bridge 运行时替换 | ❌ MC 特有 |
| ⑥ 报缺口 | 四档状态列 | ✅ 逻辑通用 |

**结论：第③步是唯一 100% 可复用的，也是唯一真正值钱的那块。**
翻译编排（分批、重试、锁文件、增量、术语库、语料喂参考、失败隔离）——
这些跟「翻译哪个游戏」毫无关系。MC 只是给它喂了个奇怪的数据源。

---

## 2. 藏在愿望里的岔路：静态覆盖 vs 运行时注入

**这是必须先做的选择，因为它决定你做一个什么样的产品。** 两者互斥，不是难度问题。

| | 静态覆盖（改文件 / 旁挂覆盖层） | 运行时注入（hook 进程） |
|---|---|---|
| 代表 | 摆渡现在的做法 | Textractor / LunaTranslator / XUnity |
| 能回滚 | ✅ 删掉覆盖层即可 | ⚠ 关掉注入即可，但注入本身有风险 |
| **能产出汉化包给别人** | ✅ 能 | ❌ 不能，每个人得自己跑一遍 |
| 覆盖面 | 只限「文本在可改文件里」 | 最大（连 exe 里的硬编码、OCR 都能吃） |
| 杀软 | 无感 | 大概率误报 |
| 游戏一更新 | 通常还能用 | 偏移一变就全挂 |
| 技术栈 | 文件格式解析 | 内存 hook / 注入 / OCR |
| 和摆渡现有手艺的关系 | 同一条线 | **另一套手艺，等于重学** |

现在的摆渡 = 静态覆盖（主线）+ MC 那边一条运行时桥（辅线）。
所以它其实已经踩了两条线，只是第二条只为 MC 服务。

**如果目标是「别人也能用」，这条路只能走静态覆盖。**
运行时注入那条赛道上已经站着三个成熟开源工具，重造没有意义 —— 你打不过 Textractor 的引擎覆盖，也打不过 XUnity 的生态。

---

## 3. 七个档位（按「能不能静态覆盖」排）

| 档 | 文本在哪 | 能静态改吗 | 现成工具 | 摆渡做这个的难度 |
|---|---|---|---|---|
| **RPG Maker MV/MZ** | `data/*.json`、`js/plugins.js` | ✅ 纯文本，改完即生效 | 一圈零散脚本 | **低** —— 最像「理想案例」 |
| **Ren'Py** | `.rpy` 脚本（纯文本） | ✅ | 官方 `renpy translate` | **低** |
| **Unity（Mono）** | `Assembly-CSharp.dll` 字符串堆 | ⚠ 能改，但要重打包/过校验 | dnSpy / Mono.Cecil | 中 |
| **Unity（IL2CPP）** | `global-metadata.dat` + `resources.assets` | ⚠ 能改，格式随版本变 | Il2CppDumper / UABEA | 中偏高 |
| **UE4 / UE5** | `.pak` 里的 `.uasset` / `.locres` | ✅ 有正规本地化机制 | FModel / CUE4Parse | 高 —— 格式版本地狱 |
| **Galgame 各引擎** | 加密包 / `.ks` / `.scn`，一引擎一套 | ⚠ 看运气 | Textractor / Luna | 高，且**一个引擎一个适配器** |
| **原生 Win 游戏** | exe 的 `.rdata`、甚至纹理图里的字 | ❌ | Textractor | 只能运行时 —— **不属于本产品** |

一句话：**「任意游戏」这个词必须收窄成「文本在可静态读取的文件里的游戏」。**

---

## 4. 抽象长什么样

如果是这个方向，摆渡要从「MC 汉化工具」变成两层结构：

```
核心层（游戏无关，已有 80%）
  输入：一批「条目」 —— 原文 + 位置 + 上下文标签（属于哪个界面/对象）
  输出：原文 → 译文的映射
  组件：engine（分批/重试）、glossary（术语）、语料、锁与增量、缺口统计

适配器层（一个引擎一个）
  ① 把该游戏的文本抽成上面那种「条目」
  ② 把译文写回去，或者生成一个覆盖层
  ③ 报告缺口（哪些还没翻）
```

**判定一个适配器够不够格的唯一标准：能不能产出「位置精确到可回写」的条目。**
产不出来的（比如只能读出来、写不回去的），就不属于这条产品线，别硬塞。

这个设计的好处：加一个新引擎 = 加一个适配器，**不碰核心、不碰 MC**。
坏处：这个抽象现在只是纸上的，**未验证**（见下一节）。

---

## 5. 建议路径：先证伪，别先做大

### 阶段 0 —— 把翻译核心和 MC 解耦（唯一没有风险的一步）
只在 MC 内部改接口，不加任何功能、不改变任何行为：
让「翻译」变成一个纯函数 —— 你给它一批条目，它还你一批译文，它不知道 MC 是什么。

- 风险：**零**（行为不变，现有测试守着）
- 收益：决定「任意游戏」以后是「加插件」还是「重写」

### 阶段 1 —— 挑第二个适配器，选 RPG Maker MV/MZ
目的**不是**多支持一个游戏，是**验证这个抽象是不是真的**。

- 判据：如果 MV 适配器能在很小的体量内跑通（读 JSON → 抽条目 → 回写 → 游戏里看到中文），说明抽象成立。
- 反判据：如果做到「快写完了还差一点」反复三次，说明抽象是假的 —— 及时止损，别硬撑。
- 为什么选它：纯文本、不用编译、改完直接开游戏见效，反馈循环最短。

### 阶段 2 —— 再挑一个形态完全不同的（Unity IL2CPP）
验证「二进制格式」这一类能不能塞进同一个框。这是抽象的最后一道考试。

### 明确不要先做的
- UE：格式版本地狱，投入产出最差
- Galgame 加密包：一个引擎一套解包，永远修不完
- 原生 exe：那是运行时路线，另一套手艺、另一个产品

## 6. 这笔账的真实成本：适配器矩阵

你现在的问题已经透露答案了：**MC 一个适配器 × 3 个加载器 × N 个版本**，已经把 L1 实机验证卡了半个多月。

换成「任意游戏」就是：**适配器(M) × 引擎版本(N) × 游戏更新频率**。

维护者只有你 + Agent，而且你看不懂代码。所以：

> **「任意游戏」的真正代价不是写第一个适配器，是此后每一个都有人来找你修。**

这也是为什么产品边界必须写死，而且要写在 README 第一屏：
**「只支持文本能被静态读取的游戏」** —— 这既是护城河，也是免责声明。

---

## 7. 翻译质量的真问题（比技术更硬）

- **MC 有现成的术语表和 CFPA 语料，换游戏一切从零。** 方块叫「下界合金」是全社区共识；换个游戏，同一个属性叫什么没人定过。
- **游戏 UI 文本比 MC 更短、更没上下文**：「Auto」「Continue」「Easy」「Apply」—— 这类词脱离界面几乎无法确定含义，比 MC 的物品名难得多（MC 至少有 `item.xxx` 命名空间提供语境）。
- 所以**「自动」的真实上限是：能读、能翻、但术语会散。**
  同一个 Attack 在三个界面里被翻成「攻击 / 进攻 / 攻击力」—— 这不是模型不行，是没有全局上下文。
- 能缓解的：同类文本聚类后一起翻、按游戏类型套预设术语包、允许用户导入自己的术语表。
- 不能消除的：**第一次翻一个新游戏，术语一定是散的。** 要有这个预期。

## 8. 三个没人提但会拦路的物理墙

### ① 字库（最容易翻车）
MC 自带 unicode 字体，所以摆渡从来没遇过这个问题。**别的游戏没有。**
- RPG Maker：字体是打包在游戏里的图片/字库文件，中文要换字库
- Unity：TextMeshPro 用预烘焙的字体图集，图集里没有汉字 → 显示方块或空白
- UE：字体资产同样要重建

**翻完显示一堆「口口口」= 白干。** 这一条能直接否掉一批游戏，必须在方案里明写。

### ② 排版（中文更短，但格子是固定的）
MC 的 tooltip 会自适应宽度。很多游戏的 UI 是像素写死的按钮/文本框：
中文虽然字少，但字宽大，反而更容易溢出或被裁。

### ③ 编码
老游戏是 GBK / Shift-JIS / 甚至自定义编码。读进来就是乱码，谈不到翻。

## 9. 法律与分发（只说一句）

自己玩：没问题。
产出汉化包分发：涉及游戏文本的复制，社区惯例是「补丁」形式，属于灰色地带 —— 各大汉化组都这么干，但这不等于没风险。真要当产品发布，这是独立话题，别在技术方案里顺手决定。

## 10. 如果只能做一件事

**做阶段 0（解耦）。**

它不新增任何功能、不改变任何行为、风险为零，但它决定了「任意游戏」以后是「加插件」还是「重写一遍」。

而这件事**恰好现在就能做** —— 它不需要开 MC，不需要实机验证，只要跑通现有测试就行。
在你「暂时没空开 MC」的这段时间里，这是唯一不阻塞的推进方向。

# 11. 同赛道开源项目（2026-11-04 调研）

## 11.1 四个主要玩家

| 项目 | 许可证 | 能搬代码吗 | 它已经解决了什么 |
|---|---|---|---|
| **LunaTranslator**（6.2k★） | **GPL-3.0** | ❌ | HOOK / OCR / 剪贴板三通道取词；**把游戏 exe 拖进窗口 → 自动转区启动 + 自动 HOOK**；支持 RPGMaker / Ren'Py / TyranoScript / Unity / Kirikiri 的**内嵌**替换；术语库、翻译缓存、多引擎（含 Sakura 本地模型） |
| **AiNiee**（6.4k★） | **AGPL-3.0** | ❌ 最不能 | **不做提取**，只吃 Mtool / Ren'Py SDK / Translator++ / ParaTranz / VNText / SExtractor 的导出文件；拖文件夹自动识别格式与语言；AI 术语表 + 禁翻表 + 替换表 + 思维链翻译 + 缓存 |
| **GalTransl**（2.4k★） | **GPL-3.0** | ❌ | gal 专用；GPT 字典（人设 / 人称代词）、译前 / 译后 / **条件字典**、缓存断点续翻；v8 加了 Agent 模式和 Tauri 桌面端；解包注入靠 GARbro / VNTextPatch 等外部工具 |
| **XUnity.AutoTranslator** | **MIT** ✅ | **可以** | Unity 运行时文本拦截；**字体替换（治中文方块）**；缓存文件是「原文=译文」；支持自定义 HTTP 翻译端点 |
| Textractor | GPL-3.0 | ❌ | 纯 hook 提取，不带翻译 |
| Translator++ | 闭源 / 捐赠 | ❌ | RPG Maker 各版本**静态提取**，商业软件占着这块 |

**你印象里那个「和 gal 汉化相关的」大概率是 LunaTranslator**（拖 exe 自动汉化就是它的招牌体验），或者 AiNiee（它才是「拖进去自动翻」的那个）。

## 11.2 许可证红线（必须先说）

摆渡是 **MIT**。MIT 项目里粘进 GPL / AGPL 代码，会导致**整个项目被迫改成 GPL / AGPL** ——
这不是道德问题，是许可证的法律效力。**AGPL 最狠**：连「通过网络提供服务」都会被算作衍生作品。

- ❌ LunaTranslator / GalTransl（GPL-3.0）、AiNiee（AGPL-3.0）：**一行代码都不能搬**，只能读思路、自己重写。
- ✅ XUnity.AutoTranslator（MIT）：可以搬，保留版权声明。
- 参考：LiteralBridge 是 Apache-2.0，你之前那个判断是对的。

**「抄思路」和「抄代码」是两件事**：架构、算法、文件格式的解析规则不受版权保护；具体实现代码受。
实践上没人会为这个打官司，但对一个要长期开源的项目，别在这上面留把柄。

## 11.3 真正的拐点：别抄代码，抄接口

摆渡的核心资产是「翻译编排 + 术语 + 本地 LLM + 增量缓存」——
**而这恰好就是所有取词工具最想要、又最不擅长的那个零件。**

于是有三条「当后端」的路，全都不用写引擎适配器：

| 做法 | 代码量 | 立刻覆盖 | 拿到的形态 |
|---|---|---|---|
| 自己写引擎适配器 | 大，一引擎一套 | 一个引擎 | 静态覆盖，**能攒可校对的译文库** |
| **当 XUnity 的自定义翻译端点** | 极小（一个本地 HTTP 服务） | **Unity 全档** | 运行时替换 + 白拿它的字体替换 |
| 当 LunaTranslator 的自定义翻译扩展 | 小（Python 扩展） | gal + 多引擎内嵌 | 运行时替换 |
| 吃 / 吐 AiNiee 的导出文件格式 | 小 | RPG Maker / Ren'Py 等已提取文本 | 静态覆盖 |

第一条要写七个适配器，后三条加起来可能还没有第一条的零头。

**而 XUnity 这条路尤其划算**：它本来就是发 HTTP 请求拿译文的设计，
摆渡起一个本地服务接住请求、用术语库 + 本地模型翻、结果进自己的缓存 ——
**Unity 那一整档位瞬间到手，还顺带拿到它的字体替换（第 8 节那堵「方块墙」它已经解决了）。**

代价要看清：走别人的运行时，拿到的是「运行时替换」，**攒不出一份可以慢慢校对的译文库**（缓存文件还是能攒）。
这正是第 2 节那条岔路在现实里的样子 —— 省力的路和你原本的产品形态不是一回事。

## 11.4 一个不太舒服但必须说的结论

**「自己玩能看懂任意游戏」这个需求，现成工具已经覆盖了 90%。**

- 你要翻的是 gal / 视觉小说 → LunaTranslator 拖 exe 就完事，质量还能接 Sakura 本地模型
- 你要翻的是 RPG Maker / Ren'Py → AiNiee + 对应 SDK 提取，也是一条成熟流水线
- 你要翻的是 Unity → XUnity 装上就能跑

摆渡重新做一遍这些，边际价值很低。

**但有一个真空确实存在：没人做「拖入游戏目录 → 自动识别引擎 → 静态提取 → 翻译 → 静态回写」的全自动一条龙。**
原因不是没人想到，是**提取这一步太脏** —— 每个引擎一套格式、一套加密、一套版本差异。
LunaTranslator 用 HOOK/OCR **绕过**了提取，AiNiee 干脆**甩锅**给外部提取器。
这条真空是「脏活没人干」，不是「技术没人想到」。

所以判断标准很简单：**你先花一小时装 LunaTranslator，把你想翻的那个游戏拖进去试试。**

- 它翻得动、翻得还行 → 摆渡不必做这件事，省下一个季度
- 它翻不动 / 内嵌排版烂 / 术语乱七八糟 → **那才是真空，而且真空在「翻译质量」，不在「提取」** —— 正好对应 11.3 的「当后端」

这个判断顺序别搞反。先验证需求存在，再讨论怎么造。

# 12. 需求重新定位（2026-11-04，他说完真实动机之后）

> 第 11 节的前提是「他要翻一个能翻的游戏」。实际动机不是这个。
> 原话要点：① 用 LunaTranslator 翻过《朝鲜之旅》，**体验巨难受**；
> ② 不只是 gal；③ 那天群友遇到**自定义加密的汉化搞不定**；
> ④ 摆渡要做的是「**小众、没人汉化**的小众游戏」。

## 12.1 第 11 节的判断错在哪

我拿「现成工具已覆盖 90%」当作劝退理由 —— 那个 90% 是**有人做、能做、值得做**的游戏。
他要的恰恰是**没人做的那个 10%**。这两个不是同一个市场：

| | 有人汉化的游戏 | 他要的小众游戏 |
|---|---|---|
| 术语来源 | Wiki / 汉化组 / CFPA / 官方中文 | **什么都没有** |
| 提取工具 | 有人做过适配器 | **没人做，得现场逆向** |
| 运行时方案 | Luna / XUnity 能跑 | 加密 + 私有格式，HOOK 也难 |
| 值不值得做 | 轮不到摆渡 | **只剩摆渡** |

所以第 11 节那套「当别人后端」的策略，在这个定位下是**错的** —— 它服务的是那 90%。

## 12.2 静态提取是对的，而且理由比「好用」更硬

运行时替换（HOOK/OCR）那次「巨难受」不是偶然，是这个方案的结构性缺陷：文字贴在屏幕上、和游戏原生排版打架、断句错位、没有沉浸感。而对**小众游戏**还有额外的问题 —— 加密和私有格式让 HOOK 也抓不到。

静态提取有三个运行时不具备的性质：

| | 静态提取 | 运行时替换 |
|---|---|---|
| 译文能不能沉淀 | ✅ 一份文件，可以反复校对、慢慢磨 | ❌ 每次现翻，缓存也只是缓存 |
| 能不能离线 | ✅ | 看引擎 |
| 排版 | ✅ 原生渲染，跟游戏自己的字体/换行走 | ❌ 全靠外挂层对齐 |
| 依赖游戏能跑 | ❌ 不需要 | ✅ 必须跑起来 |
| 拦路虎 | **加密 / 私有格式 / 回写** | 引擎适配、杀软、反调试 |

**「可沉淀」这条是关键**：小众游戏没人校对你的译文，只有你自己，所以译文必须是一份能坐下来慢慢改的静态文本，而不是一闪而过的屏幕文字。

## 12.3 「自定义加密」不可能产品化成「支持列表」

一个游戏一套加密。写成「支持 N 个游戏」的列表 = 无限适配器矩阵，而维护者只有你 + Agent，你还看不懂代码。

**但这个死结有一把钥匙：让 Agent 现场把新格式学会。**
这跟你的「AI 本地总结文本库」是同一个念头的两面 —— **不是让程序预设一切，是让 AI 每次现场解决一个新问题。**

于是摆渡的形态应该是「**AI 可编程的提取工作台**」，而不是「支持一堆引擎的汉化器」。工作台要提供的能力：

1. **字节侦查**：熵曲线、可打印字符串提取（ASCII / UTF-16 / CJK）、重复块检测（找加密边界）
2. **格式指纹**：常见引擎魔数（`UnityFS`、`xp3`、Ren'Py 的 `rpyc` 版本 magic、RPG Maker 的 Marshal 头……）
3. **解密候选生成**：单字节 XOR 爆破 + 频率分析、多字节 XOR 的密钥长度检测、常见压缩（zlib / gzip / lz4 / zstd）探测、Base64 与自定义表
4. **脚本沙盒**：Agent 写一小段解析规则，立刻在样本上跑，看解出来的是不是人话，通过就存成「适配器脚本」
5. **回归验证**：文本条数、长度分布、重复率是否合理（全是乱码或整片重复 = 解错了）
6. **沉淀**：适配器脚本按「引擎 + 加密特征」入库，下次同类游戏直接命中

第 4、6 条是核心。它把「逆向一个游戏」从「一次性的手工活」变成「一次投入、可以复用和迭代的资产」。

**顺便纠正一个常见误解**：小众游戏通常**不是**加密最狠的那一类。大厂才做专门防破解；同人/小团队的加密多半是引擎打包工具**默认带的**（Kirikiri 的 xp3、Unity 的 AssetBundle）——
默认加密往往有现成解包库，真正难的是「作者自己加的那一层」。所以先侦查、别先害怕。

## 12.4 「先总结再翻译」是对的，而且应该比翻译更早

你的想法（AI 本地总结文本库）在做小众游戏时不是锦上添花，是**唯一的术语来源**。

位置要提前到翻译之前，一次通读全部文本，产出四样东西：

| 产出 | 用在哪 |
|---|---|
| 世界观摘要 | prompt 背景设定 |
| 人物表（称谓 / 关系 / 语气） | 人设 prompt、称谓一致性 |
| 专有名词表（地名 / 技能 / 物品 / 组织） | 灌进 glossary |
| 文体判断（口语 / 古语 / 敬语层级） | 决定译文的腔调 |

三个必须守住的规矩：

- **术语必须有出处**：总结出来的每个专有名词都要能在原文里定位到具体位置，否则就是模型编的。
- **总结与翻译分开两轮**：同一轮里既总结又翻译，模型会为了自圆其说而虚构设定。
- **总结结果要落盘成文件**（人可读、可手工改），不能只活在 prompt 里 —— 你要能在翻到一半时进去改一条称谓。

## 12.5 生死点：回写

**这是整个方向最容易被忽略、也最可能一击致命的地方。**

「能解出来」和「能写回去」是两件事：

| 情况 | 后果 |
|---|---|
| 标准格式（RPG Maker JSON / Ren'Py rpy / 无加密 xp3） | ✅ 改完直接生效 |
| 默认加密但有打包工具 | ⚠ 要能重新加密并保证游戏认 |
| 自定义加密、只解得出打不回 | ❌ **要么 patch 游戏解密函数让它读明文，要么退回运行时** |
| 文本在 exe / 图片纹理里 | ❌ 只能运行时或 OCR |

**所以判断一个游戏值不值得做，第一个问题不是「能不能提取」，是「能不能回写」。**
提取成功但写不回去 = 白干，而且是在翻完之后才发现 —— 这个坑必须前置。

这条跟你的「测试真实」是同一条底线：**先验证闭环，再投入翻译**。
最小验证闭环 = 解出一个文件 → 改一句话 → 打包回去 → 进游戏看到那句中文变了。四个步骤全部通过，才允许开始翻译。

## 12.6 这个方向的护城河与代价

**护城河**：小众游戏的汉化本来就没人做，做的人要么手工、要么放弃。一个「能现场学会新格式」的工作台，在这个市场里没有对手 —— 因为对手需要先有一个团队。

**代价**：
- 每个 L3 游戏仍然是一次新的逆向，**不可能靠加适配器线性扩张**
- 工作台本身（侦查/沙盒/验证/沉淀）是个不小的工程，而且它的价值取决于「Agent 能不能真的用它」，这**未验证**
- 加密强度高的游戏就是做不了，要有明确放弃的判据（比如「三小时侦查无进展就放弃这个游戏」）

**一句话**：这条路的形态不是「汉化器」，是「**汉化工作台 + 一个会用它的 Agent**」。
这也正好回答了你那个问题「为什么记得 Luna 这么清楚」—— 因为你已经亲身试过「现成工具的天花板」在哪。

| | 形态 A：i18n 已搭好，缺内容 | 形态 B：i18n 缺位 |
|---|---|---|
| 表现 | 有 lang 文件 / 多语言 CSV / 资源包 | 文本硬编码在代码、加密包里、甚至图片里 |
| 汉化动作 | **往表里填一列** | 逆向文件格式、解密、定位文本、改代码 |
| 回写风险 | 低（改明文文件） | 高（要能重新打包/加密） |
| 本例 | ✅ | ❌ |
| 群友那个 | ? | ✅（大概率） |

**关键判断：形态 A 的成本是形态 B 的约 1%，而形态 A 在小众游戏里并不罕见** ——
原因是海外发行天然需要多语言框架，作者一旦做了框架，加中文就只是填表。

摆渡如果只能做一件事，做形态 A 的「一键识别 + 填表 + 回写」性价比远高于做形态 B 的逆向。
**而形态 A 的入口很可能就一句话：扫一遍目录，看有没有 lang 文件 / 多语言 CSV / `_key` 分区标记。**

## 13.4 意外收获：这个样本天然是个「评测集」

它已经有 **2790 条现成的中英对照**。这意味着：

> 摆渡跑一遍翻译，把这 3027 条重新翻一遍，跟已有的中文逐条比对 —— **一致率就是一个客观指标**。

这比「翻完看着顺不顺眼」硬得多，而且完全符合「测试真实」那条底线。
**建议把「这游戏」记成第一个基准样本（benchmark）**，而不是第一个目标。

## 13.5 一个待排除的疑点：字体

目录里有个 `HCRBatang.ttf`（28 MB，韩文字体），而游戏支持中 / 俄 / 西。
**如果中文显示成方块、缺字、或者只有部分字正常，那是字体问题，不是文本没翻。**

这两种病的修法完全不同：
- 文本没翻 → 填 CSV
- 字体缺字 → 换字体 / 补字形 / 改渲染

所以「没汉化完全」这个描述，得先分清是哪一种。

## 13.6 侦查手法本身值得沉淀

这次没装任何工具、没碰游戏本体、没读一句剧情，靠四步定案：

1. `ls` 看目录 → 认出 `data.win` + `GMLive` + `.exe`
2. 读 64 字节魔数 → 确认 GMS2 且未加密
3. 读小文件（`dialogue_english.txt` 96 字节、`options.ini` 59 字节）→ 发现是调试残留与运行时配置
4. **在 data.win 里数关键字出现次数**（`main_menu_button_names_key` 出现 1 次、`all_text_languages` 出现 1 次、俄文句子 0 次）
   → 反推出「文本不在 data.win 里，游戏读外置 CSV」

第 4 步是最省事的一招：**不需要解包，只要「某个文本是否存在于这个文件里」这一个布尔答案，就能判断文本到底住在哪。**
这就是工作台该有的第一个能力 —— 而它现在只是一段二十行的 Python。

# 14. DLsite 同人游戏的格式地图（等样本时先备着）

> 背景：群友那个游戏来自 DLsite，打算 AI 汉化，但被告知「小众自定义加密，解不了包」。
> 这张表是为了**样本一到就能三十秒定位**，也为了判断「解不了」这句话到底可不可信。

## 14.1 常见引擎 × 特征文件 × 可解性

按 DLsite 上的出现频率排：

| 引擎 | 认它的特征 | 文本/资源位置 | 解包 | 难度 |
|---|---|---|---|---|
| **RPG Maker MV/MZ** | `Game.exe` + `www/` 或 `game.json` | `www/data/*.json`（明文） | 直接读 | 极低 |
| **RPG Maker XP/VX/Ace** | `Game.ini` + `Data/*.rxdata` / `.rvdata2` | Ruby Marshal | 直接读 | 低 |
| **Wolf RPG Editor** | `Game.exe` + **`Data.wolf`** 或 `Data/` 目录 | `Data.wolf` 内（Shift-JIS 结构）或 `Data/` 下的 `.dat` | WOLF 系解包工具 | **中** |
| **Kirikiri / KAG** | `*.xp3` | 包内 `.ks` / `.scn` 脚本 | GARbro / KrkrExtract | 低~中（看 filter） |
| **SiglusEngine** | `SiglusEngine.exe` + `Scene.pck` | `.pck` 内场景脚本 | GARbro / SiglusExtract | 中 |
| **BGI / Ethornell** | `BGI.exe` + `.arc` | `.arc` | arc_unpacker / GARbro | 中 |
| **Majiro** | `majiro*.exe` + `.arc` | `.arc`（常带自定义密钥） | GARbro | 中偏高 |
| **NScripter** | `nscript.dat` / `*.nsa` | 文本常做 XOR 混淆（密钥 `0x84`） | 手写二十行 | 低 |
| **TyranoScript** | `tyrano/` + `data/` | `data/scenario/*.ks` | 直接读 | 低 |
| **Unity** | `UnityPlayer.dll` + `*_Data/` | `resources.assets` / AssetBundle | AssetRipper / UABEA | 中 |
| **Artemis / LiveMaker** | `.pfs` / `.dat` | 包内 | GARbro | 中 |
| **真·自研** | 以上都不像，目录里只有一个 `exe` + 一个怪后缀 | 未知 | 逆向 | 高 |

**关键点：GARbro 一个工具就覆盖了上面将近一半的格式**（Kirikiri / BGI / Majiro / Artemis / LiveMaker / Siglus 等）。
DLsite 的日本同人生态里，绝大多数所谓「自定义格式」其实是被这套工具覆盖过的老格式 —— **只是名字没人认得出来**。

## 14.2 「解不了」这句话，先按这三条甄别

AI 说「自定义加密、无法解包」，很可能只是**它没见过这个格式**，而不是这个格式真的无解。

| 甄别点 | 可信的样子 | 多半在猜的样子 |
|---|---|---|
| ① 它看过字节吗 | 引用了具体偏移、熵值、魔数、密钥长度 | 只看到文件名列表或一句报错 |
| ② 特征文件 | 能指出 `.xp3` / `Data.wolf` / `.pck` / `.arc` 这类具体名字 | 「一些加密文件」 |
| ③ 熵值 | 高熵（≈8.0）= 加密或压缩；中熵（5~7）= 打包未压缩；低熵（<5）= 明文 | 没提 |

**没有第 ① 条的结论，基本等于猜。**

## 14.3 就算真解不了包，也不等于汉化不了

三条后路，按成本从低到高：

1. **游戏可能读外部文件**（今天那个 GameMaker 就是 —— 包好好的，文本却在外面的 CSV 里）。
   验证法：在打包体里搜某个已知文本，搜不到 → 说明文本住在别处。
2. **文本可能在 exe 的字符串表里**（小引擎常见）。搜 UTF-16/Shift-JIS 字符串就能捞出来。
3. **patch 解密函数，让游戏读明文**。这是汉化组的老手艺，Wolf / Kirikiri 上都有人这么干过：
   不跟加密较劲，改成让它绕开加密。

所以判断顺序永远是：**能不能回写 > 能不能解包**。
解得出但打不回，等于没解；解不出但能 patch 成读明文，反而成了。

# 15. 案例：八星帝（RaiJin 8）—— 「AI 说解不了」到底错在哪

> 2026-11-04。群友的游戏，来源 DLsite，被 AI 判为「小众自定义加密、无法解包」。

## 15.1 判定

| 项 | 结论 |
|---|---|
| 正式名 | 八星帝 / 8th Raizin / RaiJin 8（雷神7 的正统续作） |
| 社团 | だいふく船団（大福船団），2024-02-09 发售，当前 v2.18X |
| **引擎** | **HSP（Hot Soup Processor）** —— 日本同人圈 1996 年起流行的通用游戏制作环境 |
| 文本编码 | **Shift-JIS**（Windows 版 HSP 固定用 SJIS） |
| 文本位置 | 编译后的脚本对象里（`.ax` / 打进 exe），不在明文文件里 |
| 数据文件 | 有 `eve/` 目录，`e[xxx]` 事件 / `p[xxx]` 玩法 / `x[xxx]` / `si[xxx]`（**用 CSV 存场景设定**）/ `sn[xxx]` 场景介绍 |

**证据**：雷神7 的玩家讨论里明确提到「haven't read the **`.hsp` source code**」、
「files … are in Japanese Encoding (**SHIFT-JIS**)」—— 这是 HSP 的指纹。

## 15.2 「自定义加密」这个判断，错在两个地方

1. **不是自定义**：HSP 是一个公开的、有文档有社区的引擎，不是作者自己造的格式。
2. **不是无解**：HSP 有反编译器，而且是开源的。

| 工具 | 说明 |
|---|---|
| **deHSP**（GitHub `xsyetopz/deHSP`） | C# / .NET 写的 **HSP 2/3 反编译器**，Avalonia GUI，原始算法来自 Kitsutsuki |
| HSP逆コンパイラ 1.20 | 日文老工具，支持 HSP2 / HSP3，体积只有 126 KB |
| **OpenHSP / HSP3** | HSP 本体已开源，**BSD 许可证**（跟 MIT 兼容，可以正当借鉴） |

HSP 的编译链是 `.hsp` → `hspcmp` → `.ax`（对象码）→ 运行时执行。
**反编译器吃的就是那个 `.ax`。** 所以「拿不到文本」这个结论，技术上站不住。

## 15.3 但汉化者说「很难破解」，这句是真的

找到已有汉化版的作者留言（甜族星人，v2.18X 内嵌精翻）：

> 「这作的系统和上作不一样，**很难破解**，还好程序员很厉害破解了才能汉化。」
> 「由于同样的改了游戏系统，所以杀毒程序很容易会说档案中的 **`winmm.dll`** 是病毒，这是没法避免的问题。」

这两句信息量极大：

- **「很难破解」** → 作者在 HSP 基础上加了东西（混淆插件、脚本打包、或校验），不是裸的 `.ax`
- **`winmm.dll`** → 汉化用的是 **DLL 代理注入**：把系统自带的 `winmm.dll` 换成自己的，游戏启动时加载它，在内存里替换文本。杀软报毒是这类手法的必然副作用

## 15.4 最重要的一条结论：运行时 ≠ 体验差

《朝鲜之旅》那次用 LunaTranslator「巨难受」，让人容易得出「运行时方案都不行」的结论。
**这个案例说明不是。** 两种运行时是两回事：

| | 外挂悬浮窗（Luna 默认） | DLL 内嵌替换（本案例） |
|---|---|---|
| 文字画在哪 | 独立窗口浮在游戏上 | **游戏自己的渲染层里** |
| 排版 | 全靠外挂对齐，容易错位 | 跟原生文本一样，随游戏走 |
| 沉浸感 | 差 | 好 |
| 典型工具 | Luna / Textractor | 汉化组的 DLL 代理（`winmm` / `d3d9` / `version`） |

**「运行时」不是体验的原罪，「外挂」才是。**

这条对摆渡的意义很大：摆渡在 MC 上做的 `ferrybridge` 就是「挂进游戏、改它自己的消息渲染」——
**它本来就有运行时基因，而且做的正是「内嵌」这一档，不是外挂那一档。** 这套思路可以直接平移。

## 15.5 这个案例的教训（对工作台的要求）

1. **别接受「AI 说解不了」这个结论**。要问：它说的「自定义」到底是哪个引擎？给出引擎名，就有工具链可查。
2. **「冷门引擎」和「自定义加密」是两类问题**：前者有现成工具和社区，后者才真的一个游戏一解。
3. **回写仍然是拦路虎**：HSP 编译后的 `.ax` 改字符串受长度与偏移约束，所以汉化组选了运行时替换而不是静态回写。
   这个案例里，**回写过不去，路就自动拐到运行时** —— 印证第 12.5 节的判断。
4. **已经有人做完的，先别重做**：这作已有 v2.18X 精翻汉化。要自己玩的场景下，直接用比自己造工具更划算。
   摆渡的价值在「没人做过的那些」，而不是「已经有人做过的」。

### 三条修订

1. **「明文搜不到 ⇒ 自定义加密」不成立。** 搜的是 2.5 GB 媒体包 + 2.26 MB 脚本包里的一句台词；媒体包里本来就没有台词，搜不到是必然结果，不是加密证据。要解的只有那 **2.26 MB**，2.5 GB 一趟都不用碰。

### 另一条修正：字库墙不存在

剧情已是中文且截图显示正常 → 运行时渲染中文这条路已经通了，第 8 节担心的字体/编码问题在这作上已被前汉化解决。于是 `.ax` 里的字符串走同一条渲染路径，不存在「翻完一屏口口口」。

### 判据

### 沉淀（按可复用度排序）

1. **dump > 逆向**：自制运行时的加密，优先让程序自己解、从内存取结果。
2. **等长替换 > 重打包**：编译后二进制的原位文本替换，能不重排就不重排。
3. **标点后处理**：240 条双逗号这种，是管线缺一道 `postprocess`，零风险、当天可做。

### 16.2 回写机制（这是本次最值钱的一条）

**`package.nw` 文件夹覆盖对 Chromium 41 的 nw.js 无效** —— 实测：把整包解到 exe 旁边，改一句，
游戏仍然读内嵌 zip（XHR 取 `first.ks`，`indexOf(测试标记) = -1`）。

正确姿势：**解 zip → 改 → 重建 zip → 拼回 exe 尾部**（前缀原样保留，产出副本）。
实测：重建后 XHR `indexOf = 188`，进游戏截图确认中文正常、无方块、换行未乱。

推论（写进适配器契约）：**「能不能写回去」必须在开工前回答**。这游戏的答案藏在容器格式里，
不在剧本格式里。先翻三千行再发现写不回去，就是全废。

### 16.3 文本单元的粒度

今天的替换表是「**一行 = 一个单元**」：`原文整条 → 译文`，标签原样保留在两侧。
应用器三条铁律（与本体 MC 侧同源）：
1. 一条原文**只替换一次**，出现 0 次或多次**直接报错**，不许静默跳过；
2. 只动文本，不动 `[r]/[l]/[cm]/[p]` 的位置；
3. 保留原文件 BOM 与换行风格。

这正好能塞进现有的 `Entry`：`rel_path` = 文件、`key` = `文件#行号`、`english` = 原文，
`json_pointer` 存行号。**不需要改数据结构。**

### 16.4 验证机制（差异化能力，别浪费）

nw.js / Electron / Chromium 内核的游戏都能加 `--remote-debugging-port`，然后用 CDP：
- `Runtime.evaluate` 直接读 DOM，断言「此刻屏幕上是不是中文」；
- `Page.captureScreenshot` 拿页面像素，不受窗口遮挡、不看用户桌面；
- `Runtime.exceptionThrown` 抓引擎异常。

今天全靠这条链路验完，全程没让用户点一下。**别的汉化工具不做这层，摆渡可以做。**

### 16.5 适配器该切在哪（用真实代码反推）

本体里 `translate_entries(entries: list[Entry], settings, ...) -> dict[str, dict[str, str]]`
**本来就是引擎无关的**：吃一个扁平 Entry 列表，吐一个「原文 → 译文」字典。
MC 特有的东西全在它两侧：前有 `scan_inputs()`，后有 `write_pack()`。

所以接新引擎不需要碰核心，只需要在两侧各开一个口：

```
probe(dir)      -> Report(engine, readable, writable, verifiable, unit_count, images_with_text)
collect(dir)    -> list[Entry]           # 复用 identity：原文整条当 key
apply(dir, map) -> Report(applied, missed, skipped)   # 回写 + 自检
verify(dir)     -> Report(ok, evidence)  # 起游戏 → 读 DOM → 断言 → 关掉
```

`probe` 的四个布尔值是给用户看的第一屏，缺一个都不该开始翻：
可读（能不能取到文本）／**可写（能不能放回去）**／可验证／有多少行。

### 16.6 别按引擎排，按「容器 × 文本格式」排

这是他「按引擎普及度一点点加」的想法里最该改的一处。
一个游戏能不能汉化，卡点几乎从不在引擎，而在**容器**：

| 容器 | 代表 | 回写方式 |
|---|---|---|
| zip 追加在 exe 尾部 | nw.js（今天这个） | 重建 zip 拼回尾 |
| 纯目录散装 | 大量 Unity / RPG Maker | 直接改文件 |
| xp3 / arc / pck / wolf | Kirikiri / BGI / Siglus / WOLF | 需要打包器 |
| rpa / rpyc | Ren'Py | 官方工具即可 |

文本格式是另一个正交维度：`.ks` 标签行 / `.rpy` 脚本 / JSON / CSV / TJS 字符串。
**两个维度组合复用，而不是一游戏一个适配器** —— 这是不变成「适配器矩阵」的唯一办法。

### 16.7 必须能报「翻不了的东西」

这作的标题按钮是 PNG 图片（`hajime.png` / `tuduki.png`），文本层永远翻不到。
适配器报告里必须有这一栏：图片文字 N 处 / 特殊字体 / 预渲染 UI。
不报，用户就会以为「翻完了怎么还有日文」，而这是**结构性的**，不是漏翻。

### 17.1 实测抓到的五个坑（都不在纸面设计里）

拿第 16 节那个游戏跑真数据，一路撞出来的：

1. **副本会被当成原版。** 产出 `xxx.cn.exe` 之后，`sorted(glob("*.exe"))` 里它排在
   `xxx.exe` 前面（`.` < `e`），第二次运行就读到副本，翻的是「已经没有原文的文本」。
   现在 `open_container` 显式跳过 `.cn.exe`。
2. **JS 代码被当台词。** `$(".layer_camera").empty();`、`tf.current_bgm_vol=parseInt(...)`
   各被抽了一百多次。根因是 `[iscript]` 块里的行不以 `[` 开头，看起来就是正文。
   现在有两道防线：块内整块跳过 + 代码特征（`();{}` / `tf.` / `parseInt`）排除。
3. **资源路径被当台词。** `title/button_start.png`、`chara/akane/normal.png`
   被判成「两个英文单词」。根因是判据「≥2 个 4 字母单词」完全不成立。
   现在的判据顺序是：**先排资源路径，再看有没有中日韩字符，最后才轮到拉丁文多词**。
4. **标签属性不能猜。** 早先版本把标签行里所有引号值都当候选，于是
   `storage="..."`、`target="*start"` 全进来。现在只认有语义的属性名
   （`text` / `title` / `jname` / `message` / `caption`）——
   Tyrano 显示角色名用 `jname`，`name` 是内部 ID，翻了会把存档搞坏。
5. **官方示例剧本占了七成。** `scene1.ks` 是 Tyrano 自带教程（147 条），
   第一行就写着「ティラノスクリプトサンプルゲーム」，全文唯一带 `tyrano.jp`。
   默认跳过，`--include-samples` 可强制翻。
