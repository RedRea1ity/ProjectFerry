# 摆渡桥（FerryBridge）—— NBT 文本翻译桥接模组 · 立项计划

> 状态：规划中，未开工。本文档是 2026-10 定下的方向和边界，防止做到一半跑偏。
> 前置共识：摆渡计划本体只动语言文件（lang key），NBT 里的文字（自定义物品名、
> Lore、成书、实体 CustomName）是资源包永远覆盖不到的盲区。桥接模组是补这个
> 盲区的唯一现实路径——但必须守住「不改存档、只在显示层替换」的底线。

## 一句话

一个**纯客户端**的小模组：游戏渲染文本时，用摆渡计划导出的「英文原文 → 中文」
映射做**精确替换**，让 NBT 里的英文在屏幕上显示成中文。存档一个字节都不动，
删掉模组就回到原样——和摆渡计划本体「到岸即离」同一个哲学。

## 原理（为什么可行）

NBT 文本最终都要经过渲染层：物品名和 Lore 走 tooltip 渲染，实体名走名字牌渲染，
成书走书页渲染。这些环节在 Forge/NeoForge 都有公开的事件钩子（如
`ItemTooltipEvent`、`RenderNameTagEvent`），在钩子里把匹配中的英文换成中文即可。
替换是逐帧发生的显示层行为，不写回 NBT，因此：

- 不碰存档、不碰模组本体（守 R2）；
- 只做**精确匹配**：英文原文完全一致才替换（对照表来自摆渡计划扫描时的真实
  en_us 原文），不做模糊匹配，避免误伤玩家自己写的东西；
- 玩家手写的书、告示牌永远不在映射表里，天然安全。

## 数据流

```
摆渡计划（导出按钮）                    摆渡桥（客户端模组）
────────────────────                ────────────────────
扫描 en_us + AI/社区译文             启动时读 config/ferrybridge/
生成 bridge/translations.json  ──→    translations.json
  结构: {                              构建 {英文原文: 中文} 哈希表
    "格式版本": 1,                     渲染钩子里查表替换
    "模组ID": { "English text": "中文" }
  }
放进实例 .minecraft/config/ferrybridge/（或手动拷贝）
```

- 映射表是「英文原文 → 译文」，与资源包的 key 无关——因为 NBT 里躺的就是原文。
- § 格式码：替换前把目标串按 `§` 切段、只比对纯文本段，替换后保留原格式码位置。
- 主程序侧加一个「导出桥接映射」按钮（导出全部/仅选中模组），导出后自动拷到
  检测到的实例 config 目录。

## 分期

| 阶段 | 内容 | 判定标准 |
|---|---|---|
| M1 | 1.20.1 Forge（作者实例）：物品名 + Lore 的 tooltip 替换；导出按钮；热重载（游戏内按键重读映射表） | 装了带 NBT 文本的模组后，打开物品能看到中文 Lore；F3+R 重载无需重启 |
| M2 | 成书页面文本 + `RenderNameTagEvent` 实体自定义名 | 书页中文、生物头顶名字中文 |
| M3 | 聊天栏（ClientChatReceivedEvent，默认关、设置里开）| 可选开关生效，性能无感知退化 |
| M4 | NeoForge / Fabric 移植；跟随摆渡计划支持的版本矩阵出对应构建 | 每个支持的 MC 版本有对应桥接构建 |

## 技术红线（沿用本体约定）

- R1/R2 照旧：绝不写存档、绝不改模组文件；桥接只存在于内存中的渲染替换。
- 精确匹配、原文未命中就原样显示；绝不整段正则乱替换。
- 仅客户端模组；进服务器不向服务端声明任何能力，被踢就说明实现错了。
- 性能：tooltip 每帧触发，查表必须是 O(1) 哈希命中；未命中路径零分配。

## 风险与边界（先说清楚，避免预期错位）

- 模组 NBT 结构千奇百怪：**只有最终走到渲染层的文本才救得回来**；存在 NBT 里
  但从不渲染的（如内部标记）不需要也不应该翻译。
- 映射表来自「扫描时该模组实际使用的 en_us」，模组更新导致原文变了 → 未命中
  → 显示英文。这是精确匹配的代价，重新扫描导出即可。
- 多人服客户端模组合法性：纯显示层替换等价于语言包，绝大多数服务器允许；
  但个别反作弊可能误报，遇到即卸载，不强推。
- 工作量主体在 M1 的 Forge 工程搭建（gradle、映射、签名），而不是替换逻辑本身。
